# 커뮤니티 운영·신고 처리 현황

## 문서 범위

이 문서는 현재 저장소에 구현된 신고·차단·운영 조치 기반과 아직 구현되지 않은 운영 절차를 구분한다. 실제 Supabase 프로젝트, 운영자 콘솔, 운영자 권한으로 처리하는 검수 흐름은 이 작업에서 실행하지 않았다.

## 상태 기준

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| 신고 데이터 구조 | 코드 확인 | `reports`가 게시물·댓글·프로필·크루 신고를 저장한다. |
| 사용자 차단 | 코드 확인 | `blocks`와 `blockUser`가 있으며 자기 자신 차단을 거부한다. |
| 신고 접수 함수 | 코드 확인 | `reportTarget`이 2~100자의 신고 사유를 검증한다. |
| 신고자 본인 접근 제한 | 코드 확인 | RLS가 신고자 본인의 삽입·조회만 허용한다. |
| 차단 양방향 노출 제한 | 코드 확인 | `can_view_user`가 두 사용자 사이 어느 방향의 차단도 확인한다. |
| 운영 조치·이의제기 데이터 구조 | 코드 확인 | `moderation_actions`, `appeals`가 존재한다. |
| 앱 화면의 신고·차단 진입점 | 미구현 | 서비스 함수는 있으나 현재 `CommunityScreen`에는 신고·차단 버튼이 없다. |
| 운영자 검수 화면·처리 API | 미구현 | 운영 조치 테이블에 일반 클라이언트 정책·권한이 없고 별도 운영자 도구도 없다. |
| 실제 Supabase RLS 검증 | `BLOCKED_EXTERNAL` | 로컬 또는 원격 프로젝트에서 서로 다른 JWT로 실행하지 않았다. |
| 실제 신고부터 조치까지의 운영 훈련 | `NOT_RUN` | 운영자 계정과 운영 큐가 연결되지 않았다. |

## 현재 코드가 보장하는 범위

### 신고

- 대상은 `POST`, `COMMENT`, `PROFILE`, `CREW` 중 하나다.
- 신고 사유는 2~100자이며, 데이터베이스의 상세 설명은 최대 1,000자다.
- 상태는 `OPEN`, `REVIEWING`, `ACTIONED`, `DISMISSED` 중 하나다.
- 열린 신고와 검토 중 신고를 시간순으로 찾기 위한 인덱스가 있다.
- 앱의 현재 서비스 함수는 사유만 전달하며 상세 설명 입력 UI는 없다.

### 차단

- 차단 관계는 `(blocker_id, blocked_id)` 조합으로 한 번만 저장된다.
- 자기 자신을 차단할 수 없다.
- 차단 관계가 어느 방향으로든 있으면 상대 프로필·공개 게시물·반응 조회 경로에서 제외되도록 조회 함수가 연결돼 있다.
- 현재 앱 화면에는 차단·차단 해제 진입점이 없다.

### 운영 조치와 이의제기

- 운영 조치는 처리자, 대상, 조치, 사유, 만료 시각을 저장할 수 있다.
- 이의제기는 10~2,000자이며 동일한 사용자와 운영 조치 조합에는 하나만 만들 수 있다.
- 이의제기 상태는 `OPEN`, `REVIEWING`, `ACCEPTED`, `REJECTED`다.
- 일반 사용자는 자신의 이의제기만 접근하도록 RLS가 정의돼 있다.
- 운영 조치를 생성·조회·변경하는 운영자 전용 경로는 현재 저장소에 구현돼 있지 않다.

## 운영 전 필수 미완료 항목

1. 게시물·댓글·프로필·크루 화면에 신고와 차단 진입점을 연결해야 한다.
2. 신고자에게만 즉시 숨기는 화면 동작과 전역 격리를 구분해야 한다.
3. 운영자만 접근하는 신고 큐, 조치 기록, 이의제기 처리 경로가 필요하다.
4. 운영자 권한은 사용자 편집 가능 메타데이터가 아닌 별도 권한 정본으로 판정해야 한다.
5. 서로 다른 실제 사용자 JWT로 신고자 정보 비공개, 차단 양방향, 운영자 권한 상승 거부를 검증해야 한다.

## 현재 운영 가능 판정

커뮤니티 읽기 기반과 데이터 구조는 존재하지만 실제 UGC 운영을 열 수 있는 완성된 검수 체계는 아니다. 소셜 쓰기 기능은 운영자 큐와 실제 RLS 검증이 끝날 때까지 `BLOCKED_EXTERNAL`로 본다.
