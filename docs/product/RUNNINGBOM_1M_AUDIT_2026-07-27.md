# 러닝봄 100만 다운로드 제품 감사와 실행 계획

- 감사일: 2026-07-27
- 시작 main: `a3f5c5139a3514d45fd10ef72929e7d13387d33c`
- 작업 브랜치: `codex/runningbom-1m-audit-20260727`
- 목표: 한국 초보 러너가 가장 쉽게 시작하고, 실제로 계속 달리고, 대회까지 완주하게 만드는 앱
- 원칙: 확인한 코드와 공식 자료만 근거로 쓰며, 100만 다운로드나 100억 원의 결과를 보장하지 않는다.

## 0. 한 문장 결론

러닝봄은 기능 수가 부족한 앱이 아니다. 지금 가장 큰 문제는 **대회 발견 → 훈련 계획 → 오늘 훈련 → GPS·음성 코칭 → 기록 → 성취 공유**가 하나의 끊김 없는 흐름이 아니라 여러 기능으로 나뉘어 있다는 점이다.

새 기능을 더 쌓기 전에 이 흐름을 하나로 합치고, 정식 빌드 기록 신뢰도와 측정 체계를 완성해야 한다.

## 1. 실제로 확인한 것

### 확인 완료

- Expo SDK 57 기반 React Native Android 우선 앱이다.
- 홈·시작·프로그램·달력·대회·러닝화·챌린지·커뮤니티·가이드·배지·내 정보·설정·음성·인증·온보딩 등 화면이 실제로 구현되어 있다.
- 러닝화는 단순 목록이 아니라 갈래·세부 갈래·거리·수준·가격·브랜드·플레이트 필터, 추천, 비교, 상세 화면까지 있다.
- 러닝 궁금증은 커뮤니티와 분리되어 있고 검색·분류·많이 찾는 질문·비슷한 질문 추천을 제공한다.
- 배지는 SVG 문양과 단계별 시각 표현이 있으며 글자만 있는 배지가 아니다.
- 뒤로가기는 화면 이력을 보존하는 별도 내비게이션 스택을 사용한다.
- Android 음성 코치는 foreground service, TTS, MediaSession, 이어폰 해제 감지, 음성 선택을 실제로 구현한다.
- GPS 잡음 제거, 1km 구간, 경로 좌표, 자동 멈춤, 거리 안내, 부상 경고 로직이 있다.
- 대회 데이터는 자동 갱신·검증·마지막 정상본 유지 구조가 있다.
- 정식 Production 빌드는 현재 GPS 위치 권한을 제거하고, Preview 빌드에만 GPS를 켠다.
- Production의 소셜 쓰기 정책은 켜져 있지만, 실제 로그인 화면은 자격증명이 없는 Preview 체험 모드이며 정식 로그인은 아직 아니다.
- 사용자 기록과 프로그램 진행은 주로 기기 안에 저장된다.
- 9주 프로그램 실행 화면은 메인 GPS·음성 코치·활동 기록 엔진과 별도 타이머로 동작한다.
- 목표 대회 훈련 계획은 현재 보여 주는 카드이며, 훈련을 바로 시작하거나 달력·활동 기록으로 연결하지 않는다.
- 공유 카드 미리보기는 있지만 운영체제 공유에는 이미지가 아니라 주로 텍스트가 전달된다.

# A. 1등이 되려면 없어서 치명적인 것

## A1. 정식 빌드에서 믿을 수 있는 러닝 기록

- **무엇**: 사용자가 `러닝 시작`을 누르고 화면을 끄거나 다른 앱으로 가도 시간·거리·경로·구간이 끊기지 않는다. 종료 화면에서 실제 이동거리와 멈춘 시간이 정확히 분리되어 보인다.
- **왜**: 러닝 앱의 첫 번째 계약은 기록을 잃지 않는 것이다. 이 계약을 못 지키면 코칭·대회·배지의 가치도 무너진다.
- **근거 사례**: Nike Run Club은 위치·거리·페이스·구간을 기본 기록으로 제공하고, Runna는 워치에서 계획 훈련을 실행한 뒤 결과를 계획에 다시 반영한다.
- **우리 코드 어디**: `apps/mobile/app.config.js`, `domains/tracking/**`, Android location foreground service 신규 모듈, `StartScreen.tsx`
- **난이도**: 그 이상, 실제 기기 행렬 검증 포함 3~5주
- **서버 필요**: 불필요
- **새 권한 필요**: 필요. 정식 위치 권한과 foreground service location 선언. 현재 Play 심사 뒤 별도 버전에서 진행한다.
- **위험**: Play 위치 정책·배터리·제조사별 백그라운드 제한. 사용자 시작 동작 직후에만 서비스를 시작하고 종료 즉시 멈춰야 한다.

## A2. 모든 훈련을 하나의 코치·GPS·기록 엔진으로 실행

- **무엇**: 9주 프로그램이나 대회 계획에서 `오늘 훈련 시작`을 누르면 메인 시작 화면과 같은 음성·GPS·자동 멈춤·구간·활동 저장을 쓴다. 완료하면 해당 회차와 활동 기록이 동시에 갱신된다.
- **왜**: 현재 9주 프로그램은 별도 타이머라 핵심 기능을 경험하지 못한다. 사용자는 같은 앱에서 서로 다른 방식으로 달려야 한다.
- **근거 사례**: NRC의 각 계획 훈련은 오디오 가이드 런으로 이어지고, Runkeeper는 완료된 훈련을 계획 완료로 연결한다.
- **우리 코드 어디**: `domains/programs/**`, `domains/coaching/**`, `domains/tracking/**`, `app/screens/programs/**`, `StartScreen.tsx`, `AppStateProvider.tsx`
- **난이도**: 1주 이상, 안전하게는 2~3주
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요. 정식 GPS는 A1 이후 활성화하되 시간·음성 통합은 먼저 가능하다.
- **위험**: 기존 프로그램 저장 키와 완료 판정을 깨뜨릴 수 있다. 기존 ID를 유지하고 새 실행 어댑터만 추가해야 한다.

## A3. 음악을 끊지 않는 음성 코치

- **무엇**: 설정에서 `음악 줄이고 말하기`, `음악 멈추고 말하기`, `코치 음성만`을 고른다. 코치가 말할 때만 오디오 포커스를 짧게 얻고, 끝나면 즉시 돌려준다.
- **왜**: 현재 Android 서비스는 러닝 전체 시간 동안 `AUDIOFOCUS_GAIN`을 요청한다. 기기와 음악 앱에 따라 음악이 장시간 멈추거나 코치가 다른 오디오 때문에 함께 멈출 수 있다.
- **근거 사례**: Android 공식 문서는 길 안내처럼 짧은 음성은 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`으로 음악을 잠시 줄이는 패턴을 제시한다.
- **우리 코드 어디**: `modules/runningbom-coach/**/RunningbomCoachService.kt`, `services/audio/coachService.ts`, 음성 설정 화면
- **난이도**: 1주 + 실기기 검증
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요
- **위험**: 팟캐스트 같은 말소리는 음악과 달리 줄이는 것보다 멈추는 편이 낫다. 사용자 선택과 기기별 테스트가 필요하다.

## A4. 실제 계정과 기록 복원

- **무엇**: 로그인 없이 시작은 유지하되, 사용자가 원할 때 Google·Kakao·Naver·Apple 중 지원되는 계정에 연결하고 휴대폰 교체 후 관심 대회·프로그램·배지·기록을 복원한다.
- **왜**: 수개월 훈련한 기록을 잃을 수 있는 앱은 장기 사용과 유료 결제가 어렵다. 현재 로그인 화면은 체험이고 실제 계정 연결이 아니다.
- **근거 사례**: Strava·NRC·Runna는 계정을 중심으로 기기와 웨어러블 사이의 기록을 이어 준다.
- **우리 코드 어디**: `domains/identity/**`, `app/screens/auth/**`, `services/supabase/**`, DB migration·RLS
- **난이도**: 그 이상, 3~6주
- **서버 필요**: 필요. Supabase 무료 구간으로 시작 가능하나 사용량·백업·보안 운영 필요
- **새 권한 필요**: 불필요
- **위험**: 계정 병합·탈퇴·데이터 삭제·OAuth 심사. 로그인 강제 금지, 로컬 우선 유지.

## A5. 행동·품질 측정 체계

- **무엇**: 개인정보를 최소화해 `온보딩 완료`, `첫 훈련 시작`, `첫 훈련 완료`, `7일 안에 두 번째 훈련`, `프로그램 회차 완료`, `대회 목표 지정`, `공유 완료`만 익명 집계한다. Play Android vitals와 함께 충돌 없는 사용자 비율을 본다.
- **왜**: 다운로드 수만 보면 왜 사용자가 남거나 떠나는지 알 수 없다. 지금은 100만 다운로드를 향해 무엇을 고쳐야 하는지 측정할 기준이 부족하다.
- **근거 사례**: 성장 앱들은 기능 출시보다 활성화·유지율·실험 결과로 다음 결정을 한다.
- **우리 코드 어디**: `services/analytics/` 신규 adapter, 각 핵심 화면의 명시적 event, 개인정보·동의 화면
- **난이도**: 1주
- **서버 필요**: 필요. Firebase Analytics 무료 시작 또는 자체 Supabase 이벤트 집계. 원문 GPS·검색어·음성 내용은 보내지 않는다.
- **새 권한 필요**: 불필요
- **위험**: 동의 없는 과도한 수집. 광고 식별자 없이 최소 이벤트만 수집하고 거부해도 앱이 동일하게 동작해야 한다.

## A6. 실제로 공유되는 결과 카드와 설치 연결

- **무엇**: 완주 후 거리·시간·오늘의 한마디·배지 문양이 담긴 이미지를 저장하거나 카카오톡·인스타그램·문자로 공유한다. 링크를 누른 사람은 앱 설치 또는 해당 대회·챌린지 화면으로 간다.
- **왜**: 현재 공유 화면은 시각 미리보기는 있으나 실제 공유는 텍스트 중심이다. 사용자가 자랑할 결과물이 입소문의 핵심이다.
- **근거 사례**: Strava는 활동 카드와 이벤트 전단 공유를 성장 장치로 쓰고, Kakao 공유는 이미지·문구·버튼 템플릿을 지원한다.
- **우리 코드 어디**: `app/screens/community/ShareCardComposer.tsx`, 활동 완료 화면, 딥링크·설치 라우트
- **난이도**: 1주
- **서버 필요**: 기본 이미지 공유는 불필요. 추천인 귀속은 필요.
- **새 권한 필요**: 불필요. 사진 저장 대신 운영체제 공유 시트를 우선하면 저장 권한도 피할 수 있다.
- **위험**: 새 네이티브 모듈은 runtime 호환성을 바꾼다. 현재 심사 이후 적용하고, Kakao API 사용료와 쿼터를 별도 확인한다.

## A7. Play 심사 중 버전과 다음 GPS 버전의 진실한 분리

- **무엇**: 현재 심사 빌드는 `대회·시간 기반 음성 코치`로 명확히 설명하고, GPS가 없는 상태를 숨기지 않는다. 심사 통과 후 위치 기록 버전을 별도 제출하며 스토어 설명·권한 영상·개인정보 문서를 함께 바꾼다.
- **왜**: 코드에는 GPS가 있지만 정식 빌드에는 권한이 없다. 마케팅 문구가 Preview 기능을 정식 기능처럼 말하면 사용자 불신과 정책 위험이 생긴다.
- **근거 사례**: Google Play는 위치·foreground service 사용 목적을 실제 앱 기능과 일치하게 공개하도록 요구한다.
- **우리 코드 어디**: `app.config.js`, `eas.json`, Play listing, 개인정보처리방침, release runbook
- **난이도**: 3일
- **서버 필요**: 불필요
- **새 권한 필요**: 현재 버전 불필요, 다음 버전 필요
- **위험**: 기능을 과장하면 리뷰·평점·심사 모두 악화된다.

# B. 모방을 넘어설 수 있는 지점

## B1. 한국 대회 발견부터 완주까지 한 번에

- **무엇**: 대회 카드에서 `목표로 정하기`를 누르면 남은 주와 최근 기록을 이용해 계획이 생기고, 홈에는 오늘 할 훈련 하나만 뜬다. 훈련 완료마다 대회 준비도가 갱신된다.
- **왜**: 해외 강자는 기록과 훈련이 강하지만 한국 대회 접수 일정·지역·공식 링크를 깊게 다루지 못한다. 러닝봄은 이미 대회 데이터와 계획 로직을 모두 갖고 있다.
- **근거 사례**: Strava·Runna는 훈련과 기록 연결이 강하고, 러닝봄은 한국 대회 데이터가 강하다. 두 장점을 한 흐름으로 합칠 수 있다.
- **우리 코드 어디**: `domains/races/**`, `domains/programs/**`, 홈 upcoming·today 영역
- **난이도**: 2~3주
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요
- **위험**: 계획을 의학적 처방처럼 단정하지 않는다.

## B2. 초등학생도 알아듣는 한국어 코칭

- **무엇**: 화면과 음성에서 전문용어 대신 `지금은 말할 수 있을 만큼 편하게`, `다음 1분만 조금 빠르게`처럼 바로 행동할 문장만 쓴다. 코치가 왜 이 훈련을 하는지도 한 문장으로 설명한다.
- **왜**: 초보자는 기록 앱보다 불안을 줄여 주는 안내가 필요하다. 기존 코드의 쉬운 말 원칙과 131개 가이드가 이 차별화의 재료다.
- **근거 사례**: NRC도 계획에서 매주·매회 목적을 설명하지만, 한국 초보자 표현과 국내 대회 맥락은 러닝봄이 더 잘할 수 있다.
- **우리 코드 어디**: `domains/coaching/**`, `guide/knowledge.ts`, 프로그램 설명
- **난이도**: 1주 + 실제 음성 청취 검수
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요
- **위험**: 말이 너무 잦아 음악·호흡을 방해할 수 있다. 코칭 밀도 설정과 침묵 구간을 실측한다.

## B3. 실패해도 돌아오게 하는 계획

- **무엇**: 한 주를 놓치면 `처음부터`가 아니라 `이번 주를 가볍게 다시`, `한 단계만 뒤로`, `계속 진행` 세 가지를 보여 준다. 아픈 날은 걷기·회복으로 바뀌고 연속 기록이 끊겼다는 벌점을 주지 않는다.
- **왜**: 초보자 이탈은 의지 부족보다 계획을 놓친 뒤 복귀 방법을 몰라서 생긴다.
- **근거 사례**: Duolingo는 습관 장치를 쓰지만 학습과 달리 러닝은 회복이 필요하다. 러닝봄은 벌주는 연속 기록 대신 안전한 복귀로 차별화할 수 있다.
- **우리 코드 어디**: `domains/programs/progress.ts`, `recent.ts`, 홈 today 카드
- **난이도**: 1주
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요
- **위험**: 과도한 밀어붙이기 금지. 통증·피로 선택 시 휴식을 우선한다.

## B4. 러닝화 DB를 실제 기록과 연결

- **무엇**: 사용자가 현재 신발을 고르면 활동마다 자동 연결되고 누적 거리와 최근 사용일을 보여 준다. 교체를 단정하지 않고 `확인해 볼 때`라고 안내하며 목표 대회에 맞는 후보를 비교한다.
- **왜**: 135종 DB가 읽는 콘텐츠로 끝나면 재방문과 구매 연결이 약하다. 기록과 연결되면 매 러닝마다 가치가 쌓인다.
- **근거 사례**: Garmin·Strava 계열은 장비 사용량을 기록하지만 한국어 추천·대회 거리·초보자 설명은 개선 여지가 있다.
- **우리 코드 어디**: `domains/shoes/**`, `ActivityRecord`, 활동 저장·완료 화면
- **난이도**: 1~2주
- **서버 필요**: 불필요
- **새 권한 필요**: 불필요
- **위험**: 내구 수명과 부상 예방을 과학적 확정처럼 말하지 않는다. 제휴 링크는 광고임을 표시한다.

## B5. 공식 출처와 마지막 확인 시각을 제품 신뢰로 사용

- **무엇**: 대회 카드에 출처·마지막 확인·변경 여부를 짧게 표시하고, 접수 시간이 확정되지 않으면 알림을 만들지 않는다. 링크가 바뀌거나 데이터가 줄면 기존 정상본을 유지한다.
- **왜**: 대회 접수 알림은 한 번 틀리면 신뢰를 잃는다. 러닝봄은 이미 자동 검증과 마지막 정상본 구조가 있어 이를 사용자 신뢰로 바꿀 수 있다.
- **근거 사례**: 일반 러닝 기록 앱은 한국 대회 데이터 정합성을 핵심 제품으로 다루지 않는다.
- **우리 코드 어디**: `scripts/refresh-races.mjs`, `domains/races/**`, 대회 상세 카드
- **난이도**: 3일
- **서버 필요**: 현재 GitHub Actions와 정적 피드로 불필요
- **새 권한 필요**: 불필요
- **위험**: 자동 수집값을 공식 확정값처럼 보이지 않는다.

# C. 100만 다운로드로 가는 성장 장치

## C1. 완주 이미지 공유 → 해당 훈련 바로 열기

- **무엇**: 공유받은 사람은 이미지 아래 `나도 이 30분 초보 런 해보기` 링크를 누르고 설치 후 같은 훈련 설명으로 들어간다.
- **왜**: 단순 기록 자랑보다 따라 할 수 있는 행동이 있어야 신규 사용자가 된다.
- **근거 사례**: Strava 활동 공유와 이벤트 전단, Kakao 이미지·버튼 공유 패턴.
- **우리 코드 어디**: 공유 카드, 딥링크, 설치 랜딩, 추천 귀속
- **난이도**: 1~2주
- **서버 필요**: 추천 귀속·통계는 필요
- **새 권한 필요**: 불필요
- **위험**: 공유 강요 금지, 개인 경로·정확한 위치는 기본 숨김.

## C2. 대회별 준비방

- **무엇**: 대회를 목표로 정한 사람에게만 `D-30 준비`, `이번 주 훈련`, `준비물`, `공식 변경`을 묶어 보여 준다. 첫 단계는 게시판 없이 읽기 전용으로 시작하고, 이후 인증 사용자만 글을 쓴다.
- **왜**: 대회는 마감과 날짜가 있어 사람들이 같은 시기에 모인다. 일반 피드보다 목적이 분명하다.
- **근거 사례**: Strava의 클럽 이벤트·RSVP 기능은 운동 모임을 중심으로 반복 방문을 만든다.
- **우리 코드 어디**: `domains/races/**`, `community/**`, Supabase RLS
- **난이도**: 읽기 전용 1주, 쓰기 포함 3주 이상
- **서버 필요**: 쓰기·참여자는 필요
- **새 권한 필요**: 불필요
- **위험**: 허위 참가자 수·가짜 글 금지, 신고·차단·운영 정책 필수.

## C3. 친구 한 명과 이번 주 약속

- **무엇**: `이번 주 2번 달리기` 약속을 만들고 친구에게 링크를 보낸다. 둘 다 완료하면 함께 쓰는 기념 카드가 생긴다. 순위보다 서로 확인해 주는 구조다.
- **왜**: 친구 관계는 알림보다 강한 복귀 이유가 된다.
- **근거 사례**: Duolingo는 친구와 공유하는 연속 기록 사용자가 일일 학습을 끝낼 가능성이 더 높았다고 공개했다. Samsung Health도 소규모 그룹 챌린지를 운영한다.
- **우리 코드 어디**: challenges·identity·sharing·push
- **난이도**: 3주 이상
- **서버 필요**: 필요
- **새 권한 필요**: 불필요
- **위험**: 경쟁 압박과 알림 피로. 조용히 나가기와 알림 빈도 제한 필요.

## C4. 동호회·회사 5K 시작팩

- **무엇**: 운영자가 4주 또는 9주 프로그램 링크를 만들고 구성원이 참여한다. 주간 완료율만 익명 합산하고 개인 거리·위치는 공개하지 않는다.
- **왜**: 한 명씩 광고로 데려오는 것보다 회사·학교·동호회 단위로 20~100명을 데려오는 편이 빠르다.
- **근거 사례**: Samsung Health 그룹 챌린지와 Strava 클럽 이벤트는 조직 단위 참여를 만든다.
- **우리 코드 어디**: programs·challenges·invite·admin web
- **난이도**: 그 이상, 4~8주
- **서버 필요**: 필요
- **새 권한 필요**: 불필요
- **위험**: 고용주가 개인 건강정보를 보지 못하도록 집계값만 제공한다.

## C5. 대회 주최사 공식 접수 알림 파트너

- **무엇**: 주최사가 공식 접수 시각·변경·마감 상태를 제출하고 검증 배지를 받는다. 사용자는 정확한 알림을 받고 주최사는 실제 관심자에게 도달한다.
- **왜**: 경쟁 앱이 복제하기 어려운 한국 대회 공급망을 만들 수 있다. 광고보다 제품 신뢰와 매출이 함께 생긴다.
- **근거 사례**: 이벤트 플랫폼과 Strava 클럽 도구는 주최자와 참가자를 같은 제품 안에서 연결한다.
- **우리 코드 어디**: 대회 수집 파이프라인, 주최사 제출 포털, 검수 queue
- **난이도**: 그 이상, 6~12주
- **서버 필요**: 필요
- **새 권한 필요**: 불필요
- **위험**: 돈을 낸 대회를 검색 상단에 몰래 올리지 않는다. 광고·공식 제출·편집 추천을 구분한다.

## 3. 우선순위 1~10위

| 순위 | 작업 | 지금 해야 하는 이유 | 현재 심사 중 가능 여부 |
|---:|---|---|---|
| 1 | 일시정지 거리·페이스 무결성 | 기록 신뢰를 깨는 실제 결함 | 가능, 이번 브랜치에 수정 |
| 2 | 9주 프로그램을 메인 코치 엔진과 통합 | 현재 가장 큰 제품 단절 | 가능, 새 권한 없음 |
| 3 | 목표 대회 계획의 `이번 주 훈련 시작` 연결 | 대회 데이터의 차별화를 실제 사용으로 전환 | 가능 |
| 4 | 스토어 설명·기능 진실성 정리 | 정식 빌드 GPS 없음 | 가능 |
| 5 | 음악 공존 음성 코치 실기기 검증·수정 | 실제 러닝 만족도를 좌우 | 코드 가능, 네이티브 빌드 검증 필요 |
| 6 | 최소 행동 분석·충돌 측정 | 유지율 없이 성장 판단 불가 | 심사 후 SDK 추가 권장 |
| 7 | 정식 foreground GPS 기록 | 러닝 앱 기본 계약 | 현재 심사 후 별도 버전 |
| 8 | 완주 이미지 공유와 설치 딥링크 | 가장 직접적인 입소문 | 심사 후 네이티브 모듈 검토 |
| 9 | 실제 계정·복원 | 장기 사용자와 유료화 기반 | 서버·OAuth 준비 후 |
| 10 | 친구 약속·대회 준비방 | 네트워크 성장 | 핵심 신뢰도 확보 후 |

## 4. 내가 개발자라면 이 순서로 한다

첫째, 기록 오류와 프로그램 단절을 먼저 고쳐 한 번 달린 사람이 `이 앱은 믿을 수 있다`고 느끼게 한다.  
둘째, 정식 GPS·음악 공존·충돌 측정으로 실제 러닝 중 품질을 완성한다.  
셋째, 완주 공유·친구 약속·대회 준비방을 붙여 만족한 사용자가 다음 사용자를 데려오게 한다.

## 5. 출시 단계

### 단계 0 — 현재 Play 심사 중

- 새 Android 권한 추가 금지
- 새 네이티브 의존성 추가 금지
- 일시정지 무결성·순수 로직·문구·테스트만 수정
- 정식 앱에서 제공하지 않는 GPS 기능을 스토어에 과장하지 않음
- 9주 프로그램과 음성 코치의 데이터 계약 설계

### 단계 1 — 심사 통과 직후 1.0 품질 버전

- 모든 프로그램을 하나의 코치 실행 엔진으로 통합
- 오디오 포커스 3모드와 Bluetooth·음악 앱 기기 시험
- 크래시 없는 사용자 비율, 첫 훈련 시작·완료 측정
- 정식 위치 foreground service와 Play 정책 자료 준비
- 20명 이상 실외 기기 시험: 도심·공원·터널·신호등·화면 잠금

### 단계 2 — 기록 신뢰도 공개 출시

합격 조건:

- 30분 러닝 중 기록 누락 0건(시험 기기 행렬)
- 수동·자동 일시정지 중 거리 증가 0m 허용 범위 검증
- 앱 강제 종료·통화·이어폰 해제 후 상태가 거짓으로 완료되지 않음
- 크래시 없는 사용자 비율 99.5% 이상을 목표로 관찰
- 첫 러닝 시작 사용자의 완료율과 7일 재방문을 실제 측정
- 개인정보 원문 좌표는 서버로 보내지 않음

### 단계 3 — 100만 다운로드 성장 버전

- 완주 이미지 공유와 딥링크
- 대회별 준비 흐름
- 친구 한 명과 주간 약속
- 계정·복원
- 동호회·회사 시작팩
- 대회 주최사 파트너 도구

| 7일 두 번째 러닝 | 첫 러닝 뒤 7일 안에 다시 달린 비율 |
| 4주 프로그램 잔존 | 프로그램을 시작한 사람이 4주차에 남아 있는 비율 |
| 대회 목표 전환 | 대회 상세 방문 중 목표 대회로 저장한 비율 |
| 공유 완료 | 공유 화면 진입이 아니라 실제 공유 시트 완료 비율 |
| 초대→설치→첫 러닝 | 초대 링크가 실제 행동으로 이어진 비율 |
| GPS 품질 | 누락 시간·비정상 점프·일시정지 거리 증가 |
| 충돌 없는 사용자 | Play Android vitals 기준 |

## 7. 100억 목표에 대한 사업 판단

100억 원은 기능 수로 생기지 않는다. `강한 유지율 × 반복 결제 × 낮은 이탈 × 유통 구조`가 필요하다.

권장 수익 구조:

1. 기본 기록·초보 프로그램·대회 탐색은 무료
2. 고급 대회 계획·세밀한 코칭·기록 비교는 월/연 프리미엄
3. 러닝화·대회 준비물은 광고임을 밝힌 제휴
4. 대회 주최사·동호회·회사 도구는 B2B 요금
5. 일반 배너 광고는 러닝 화면과 안전 안내에는 넣지 않음

예시일 뿐 보장값이 아닌 시나리오:

- 월간 사용자 10만 명, 2%가 월 6,900원 결제하면 결제 수수료·세금 전 월 총결제액은 약 1,380만 원이다.
- 월간 사용자 100만 명, 3%가 월 6,900원 결제하면 월 총결제액은 약 2억 700만 원이다.
- 여기에 제휴·대회 파트너·B2B가 붙어야 큰 기업가치가 가능하다.

따라서 첫 목표는 `100억` 자체가 아니라 **첫 러닝 완료율과 7일 두 번째 러닝 비율을 업계 최고 수준으로 만드는 것**이다. 이 두 숫자가 없으면 광고비로 설치를 사도 사용자가 빠져나간다.

## 9. 완료 판정

이 문서는 아이디어 목록이 아니라 실행 순서다. 다음을 만족하기 전에는 `완벽한 러닝 앱`이라고 부르지 않는다.
